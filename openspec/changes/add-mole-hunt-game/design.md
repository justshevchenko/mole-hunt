# Design

## Context

Репозиторій `mole-hunt` порожній, є лише налаштування OpenSpec. Обрано стек: статичний сайт на GitHub Pages (публічний репозиторій) і Supabase (Postgres) як база даних та API. Власного сервера немає, тому все, чому не можна довіряти браузеру, виконується в SQL-функціях Supabase. Вимоги описані в `specs/`, мотивація — у `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Сайт без кроку збирання: відкривається з будь-якого статичного хостингу і локально через простий статичний сервер.
- Ігрову логіку відокремлено від DOM, щоб її можна було покрити юніт-тестами без браузера.
- Таблиці бази даних закриті для прямого доступу з браузера; запис і читання лише через SQL-функції.
- Усі правила ранжування й кубків рахуються в одному місці — у базі даних.

**Non-Goals:**
- Повний захист від ботів і автокліків: перевіряємо лише межі можливого результату.
- Захист ідентифікатора гравця: хто знає чужий ID, може грати від його імені. Для анонімної гри це прийнятно.
- Перенесення гравця між браузерами, зміна імені, обмеження частоти запитів.
- Звуки, анімації понад мінімальні, кілька мов інтерфейсу (лише українська).

## Decisions

### 1. Чистий JavaScript (ES-модулі) без збирача
Фронтенд — `index.html`, CSS і кілька ES-модулів у теці `web/`. Клієнт Supabase підключається як ES-модуль з CDN jsDelivr із зафіксованою версією `@supabase/supabase-js@2`.
- *Чому:* гра маленька, фреймворк і збирач не дають переваг, але додають крок збирання й залежності. GitHub Pages віддає файли як є.
- *Альтернативи:* Vite + React/Vue — зручніше для великих інтерфейсів, але потребує збирання в CI; тут зайве.

### 2. Структура модулів
```
web/
  index.html        екрани: старт, гра, результат (перемикаються класами)
  styles.css
  js/
    config.js       URL і публічний (publishable/anon) ключ Supabase
    engine.js       чиста ігрова логіка: стан, кроти, бали, рівні, авто
    game-ui.js      рендер поля, таймера, режимів; передає натискання в engine
    player.js       ID гравця в localStorage
    api.js          виклики SQL-функцій Supabase
    leaderboard.js  рендер таблиці лідерів
    results.js      екран результату, запит імені, кубок
    main.js         зв'язує все разом
tests/
  engine.test.js    тести для `node --test`
```
`engine.js` не звертається до DOM, `Date` чи `Math.random` напряму: час (`now`) і генератор випадкових чисел передаються ззовні. Тести керують часом вручну і перевіряють сценарії зі специфікацій `gameplay` і `difficulty` детерміновано.

### 3. Модель ігрового рушія
- Стан: `startedAt`, `endsAt = startedAt + 20000`, `score`, `mode` (`easy|medium|hard|epic|auto`), `level` (0–3), `streak`, `moles[]` (`{cell, spawnedAt, expiresAt}`), `nextSpawnAt`.
- `tick(now)` викликається з `requestAnimationFrame` (і з `setInterval` 100 мс як підстраховка): прибирає кротів з `expiresAt <= now`, додає нового, якщо `now >= nextSpawnAt` і кротів менше 3, планує `nextSpawnAt = now + random(600..1000)`, а якщо поле порожнє — не пізніше ніж через 1000 мс. Гра завершується, коли `now >= endsAt`.
- `expiresAt = spawnedAt + LIFETIME[level]` рахується в момент появи, тому зміна рівня не зачіпає кротів, які вже є на полі.
- `hit(cell, now)`: кріт є → `score + 1`, кріт зникає, `streak + 1`; в авторежимі при `streak === 3` → `level = min(level + 1, 3)`, `streak = 0`. Крота немає → `score = max(score − 1, 0)`; в авторежимі `level = max(level − 1, 0)`, `streak = 0`.
- `setMode(mode)`: фіксований режим → `level = LEVEL[mode]`; `auto` на старті → середній рівень, посеред гри — рівень лишається поточним; `streak = 0` в обох випадках.
- Обробник натискань — `pointerdown` (а не `click`) з `touch-action: manipulation`, щоб дотик спрацьовував без затримки й без подвійного масштабування.
- Таймер рахується від реального часу (`performance.now()`), тому неточність `requestAnimationFrame` чи фонова вкладка не подовжують гру.

### 4. Ідентифікатор гравця
`crypto.randomUUID()` зберігається в `localStorage` під ключем `molehunt.playerId`. Якщо `localStorage` недоступний (приватний режим із блокуванням), ID живе лише в пам'яті до закриття вкладки. Чи гравець уже зареєстрований, браузер дізнається від сервера (`get_player`), а не з `localStorage`, щоб не було розбіжностей.

### 5. Схема бази даних
```
players                               scores
+-------------+-------------+         +------------+-------------+
| id          | uuid PK     |<--------| player_id  | uuid FK     |
| name        | text        |         | id         | bigserial PK|
| guest_no    | int null    |         | score      | int >= 0    |
| created_at  | timestamptz |         | mode       | text check  |
+-------------+-------------+         | created_at | timestamptz |
                                      +------------+-------------+
sequence guest_no_seq  -- «Гість N»
```
- `name`: 1–20 символів після `trim` (check-обмеження). Для гостя `name = 'Гість ' || guest_no`.
- `mode`: check `in ('easy','medium','hard','epic','auto')`.
- Індекс `scores (player_id, score desc, created_at asc)` для вибірки найкращого результату.
- Зберігаються всі ігри, а не лише рекорд: так «час досягнення рекорду» природно береться з першої гри з максимальним балом, і ми не втрачаємо історію.

### 6. Доступ лише через SQL-функції (RLS)
RLS увімкнено на обох таблицях без жодної політики для ролей `anon`/`authenticated`, тому прямі `select/insert/update/delete` з браузера заборонені. Браузер викликає функції `security definer` з фіксованим `search_path`, право `execute` видано ролі `anon`:

| Функція | Що робить | Повертає |
|---|---|---|
| `get_player(p_id uuid)` | Шукає гравця | `name` або `null` |
| `register_player(p_id uuid, p_name text)` | Порожнє/`null` ім'я → гість з `nextval('guest_no_seq')`; інакше перевіряє довжину. Якщо гравець уже є — повертає наявне ім'я, не змінюючи його | `name` |
| `submit_score(p_id uuid, p_score int, p_mode text)` | Перевіряє гравця, `0 <= p_score <= 40`, режим. Запам'ятовує попередній рекорд, вставляє гру, рахує місце і кубок | `{score, best_before, rank, cup}` |
| `get_leaderboard(p_id uuid)` | Топ-10 і рядок поточного гравця, якщо він нижче 10-го місця | рядки `{rank, name, best, mode, is_me}` |

- *Чому:* із публічним ключем у браузері це єдиний спосіб гарантувати перевірку результату й незмінність імені без власного сервера.
- *Альтернативи:* RLS-політики на `insert` — не дають перевірити «бали не більші за максимум» з урахуванням логіки, і браузер міг би читати чужі ID. Supabase Edge Functions — потребують Deno й деплою функцій, складніше за SQL.
- **Межа 40 балів:** новий кріт з'являється не частіше ніж раз на 0,6 с, тож за 20 с максимум ≈ 20 / 0,6 + 1 ≈ 34 влучання. 40 дає запас на похибки таймерів.

### 7. Ранжування в SQL
```
best AS (
  SELECT DISTINCT ON (player_id) player_id, score, mode, created_at AS achieved_at
  FROM scores
  ORDER BY player_id, score DESC, created_at ASC   -- перша гра з максимальним балом
),
ranked AS (
  SELECT *, ROW_NUMBER() OVER (ORDER BY score DESC, achieved_at ASC) AS rank
  FROM best
)
```
`ROW_NUMBER`, а не `RANK`: рівні результати отримують різні місця за часом досягнення, як вимагає специфікація. Режим рекорду — режим тієї самої першої гри з максимальним балом. Повторення рекорду не змінює `achieved_at`, бо береться найраніша гра.

### 8. Кубок рахує сервер
`submit_score` визначає `cup` (`gold|silver|bronze|null`) за правилом зі специфікації `game-results`: `p_score >= 1`, і (`best_before is null` або `p_score >= best_before`), і `rank <= 3`. Браузер лише показує те, що повернув сервер, тож правило існує в одному місці.

### 9. Публікація
GitHub Actions workflow (`actions/upload-pages-artifact` + `actions/deploy-pages`) публікує лише теку `web/` при пуші в `main`. Тести рушія (`node --test`) запускаються в тому самому workflow перед публікацією. SQL-міграції лежать у `supabase/migrations/` і застосовуються вручну через SQL Editor у панелі Supabase (CLI не обов'язковий).

## Risks / Trade-offs

- [Безкоштовний проєкт Supabase ставиться на паузу після ~7 днів без запитів] → У README описано, як відновити проєкт; сайт показує зрозуміле повідомлення про помилку збереження і таблиці лідерів замість «зависання».
- [Публічний ключ видно в коді] → Це очікувано для publishable/anon-ключа; таблиці закриті RLS, доступ лише через функції з перевірками. Сервісний ключ у репозиторій не потрапляє.
- [Бот може надсилати результати в межах 0–40] → Прийнятно для навчальної гри (див. Non-Goals). За потреби пізніше можна додати серверну сесію гри з часом старту.
- [Чужий ID дає змогу грати від чужого імені] → ID випадковий (UUID) і ніде не показується; таблиця лідерів не повертає ID інших гравців.
- [Втрата `localStorage` (очищення браузера) = новий гравець] → Задокументоване обмеження анонімної ідентифікації.
- [Неточні таймери на слабких телефонах] → Логіка спирається на мітки часу, а не на кількість тіків; запізнілий тік лише прибирає вже прострочених кротів.
- [CDN jsDelivr недоступний] → Версію бібліотеки зафіксовано; за потреби файл можна покласти поруч у `web/vendor/`.

## Migration Plan

1. Створити проєкт Supabase (вручну, власником акаунта) і застосувати `supabase/migrations/0001_init.sql` у SQL Editor.
2. Вписати URL проєкту і publishable/anon-ключ у `web/js/config.js`.
3. Увімкнути GitHub Pages з джерелом «GitHub Actions» у налаштуваннях репозиторію; пуш у `main` публікує сайт.
4. Відкат: попередня версія сайту — повторний запуск workflow на потрібному коміті; базу можна повністю прибрати, видаливши функції, таблиці й послідовність (скрипт відкату в коментарі міграції).
